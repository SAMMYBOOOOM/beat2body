# beat2body — 2D Pipeline

Part of [beat2body](../README.md) · 2D data pipeline, model design and data format.

> Paths are relative to the repository root.

## 1. Scope and success criteria

**What "done" means**

The 2D baseline is done when, for a given audio file and a chosen dance category, the model produces a **plausible 2D skeleton sequence** that:

1. **Moves in time with the music** (beat/onset alignment is visibly better than a static or random baseline).
2. **Exhibits category-consistent motion statistics** (e.g., the distribution of joint velocities and pose configurations for "Hip-hop" differs measurably from "House").
3. **Does not collapse** to a single repetitive motion (diversity above a trivial threshold).
4. **Can be rendered** as a stick-figure video for visual inspection.

**Output format**

Store **both**:

- **Primary output:** a `.npy` or `.npz` file of shape `(T, J, 2)` containing 2D joint coordinates (pixel or normalized coordinates) at a fixed frame rate (e.g., 30 fps).
- **Secondary output:** an `.mp4` stick-figure video generated by overlaying the skeleton on a blank canvas (or on the original video for debugging).

Keeping the raw skeleton as the primary artifact ensures later comparison with 3D pipelines (where you would have `(T, J, 3)`).

## 2. Architecture baseline

| Component                 | Recommendation                                                                                                                                                           | Why it fits 8 GB                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| **Audio encoder**         | 2-layer **1D CNN** or a small **Transformer encoder** (2 layers, 4 heads, d_model=128) over log-mel spectrograms + onset strength                                        | Audio features are low-dimensional; a small encoder uses < 200 MB                                  |
| **Category conditioning** | **Learned embedding** (embedding dim 16–32) for 2 categories, projected and added to the decoder's hidden state at every step                                            | Negligible memory                                                                                  |
| **Motion decoder**        | **GRU** (1–2 layers, hidden size 256) or a **causal Transformer decoder** (2 layers) that predicts the next 2D joint vector                                              | GRU with 256 hidden units is tiny; even a 2-layer Transformer with d_model=128 is well within 8 GB |
| **Output head**           | Linear layer → `(J × 2)` per frame                                                                                                                                       | Small                                                                                              |
| **Losses**                | **MSE** on joint positions + **velocity loss** (MSE on `Δjoint`) + optional **beat-alignment loss** (pull local minima of mean joint speed toward detected audio onsets) | No extra memory; beat loss is a scalar computation                                                 |

## 3. Pose estimation tool choice

| Tool          | Accuracy                                                     |
| ------------- | ------------------------------------------------------------ |
| **DWPOSE**    | High (whole-body, robust to occlusion)                       |
| **MediaPipe** | Moderate (fast, but can struggle with fast spins/occlusions) |
| **OpenPose**  | High (but heavy)                                             |

## 4. Concrete pipeline

All code is in the `beat2body` Python package and runs as `python -m beat2body <command>` (or `beat2body <command>` after `pip install -e .`). Data lives in the data root `2d/` (change it with `--data-root`). In order:

```bash
python -m beat2body frames --limit 1                    # 4.2 (optional, JPEGs for inspection)
python -m beat2body pose dwpose --preview 2             # 4.3 (one or more of the three tools)
python -m beat2body pose mediapipe --preview 2
python -m beat2body pose openpose --preview 2
python -m beat2body clean --tool dwpose                 # 4.4 (once per tool)
python -m beat2body audio                               # 4.5 (shared by all tools)
python -m beat2body clips --tool dwpose                 # 4.6 + 4.7 (once per tool)
```

`all` runs 4.5 + 4.4 + 4.6/4.7 for several tools after the pose step:

```bash
python -m beat2body all --tools dwpose mediapipe openpose --delete-raw
```

Every step accepts `--categories` (e.g. `--categories la_hiphop house`) and `--limit N` (at most N videos per category) for a quick test; `--help` lists all options.

**To train you do not need the videos, a GPU or the pose tools**: the processed data is on Hugging Face (section 5).

```bash
python -m beat2body hf download --tool dwpose           # keypoints + features + clips into 2d/
python -m beat2body hf download --tool dwpose --parts keypoints features
python -m beat2body clips --tool dwpose --test-songs 0  # rebuild clips with other split options
```

**Requirements:** Python 3.9+, `ffmpeg` on the PATH (for videos), and the extras in `pyproject.toml`: `pip install -e ".[data]"` for training machines, `[audio]` for 4.5, `[dwpose]` / `[mediapipe]` / `[openpose]` for 4.3 (DWPose also needs `pip install --no-deps easy-dwpose`).

### 4.1 Video collection

- Source: the **AIST Dance Video Database** (refined 2 Mbps videos, advanced choreography `sFM`, front camera `c01`). All 10 genres are included, 21 videos each (3 dancers × 7), 28–48 seconds per video. Folder names: `la_hiphop` (LA-style Hip-hop, `gLH`), `house` (`gHO`), `middle_hiphop` (`gMH`), `break` (`gBR`), `pop` (`gPO`), `lock` (`gLO`), `waack` (`gWA`), `krump` (`gKR`), `street_jazz` (`gJS`), `ballet_jazz` (`gJB`).
- Files are in `2d/raw_video/<category>/` and keep their original AIST names, which encode the dancer and the song: `gLH_sFM_c01_d16_mLH0_ch01` = genre `LH`, dancer `d16`, song `mLH0`. Each genre has 3 dancers and 6 songs; every dancer dances to all 6 songs. Each video can be re-downloaded from `https://aistdancedb.ongaaccel.jp/v1.0.0/video/2M/<video_id>.mp4`.
- **Terms of use:** AIST Dance DB is free for academic research; redistribution is not permitted and the database must be cited (Tsuchida et al., ISMIR 2019). See https://aistdancedb.ongaaccel.jp/terms_of_use/.
- Other sources (YouTube Creative Commons, Vimeo, FineDance) can be added as new folders in `2d/raw_video/`.

### 4.2 Frame extraction

The AIST videos are **59.94 fps**. Everything downstream uses a fixed **30 fps**, resampled with `ffmpeg -vf fps=30` to avoid variable frame timing:

```bash
python -m beat2body frames --categories la_hiphop --limit 1
# -> 2d/frames/la_hiphop/<video_id>/000001.jpg ...
```

Optional: the pose tools read the videos directly at the same 30 fps. Dumping all 210 videos as 1080p JPEGs takes 20+ GB.

### 4.3 Pose estimation

The three tools (`beat2body/pose/`) share the same options and output format, so they can be run and compared independently:

| Command               | Model                                         | Runs on        | Native joints                     |
| --------------------- | --------------------------------------------- | -------------- | --------------------------------- |
| `pose dwpose`         | DWPose-L whole-body (ONNX)                    | GPU (or CPU)   | 134 (body 18, feet, face, hands)  |
| `pose mediapipe`      | MediaPipe Pose Landmarker (heavy)             | CPU (GPU if available) | 33                        |
| `pose openpose`       | official CMU build (`--backend official`, BODY_25) or PyTorch port (`--backend pytorch`, BODY-18, default) | GPU (or CPU) | 25 / 18 |

- Output: `2d/keypoints/<category>/<video_id>_<tool>.npz` with `keypoints` of shape `(T, 17, 3)` (x, y in pixels, confidence) in the shared **COCO-17** joint order, and `native` with the tool's own joint layout. COCO-17 has no neck or pelvis joint; the pelvis is the mid-point of the two hips.
- Frames where no person is found are `NaN`. If several people are found, the most confident one is kept.
- `--preview` writes skeleton overlay videos (`--preview N`: only the first N) next to the keypoints; `--height` runs the model on downscaled frames; `--backup-dir` (see Colab above).
- Model weights download automatically on first run (DWPose and OpenPose from public Hugging Face repos, MediaPipe from Google).
- The confidence values are on different scales per tool, so each tool has its own default threshold (DWPose 0.3, MediaPipe 0.5, OpenPose 0.1).
- OpenPose models are licensed for academic / non-commercial research only. The published OpenPose dataset was made with `--backend official` (built by `scripts/colab_build_openpose.sh`).

### 4.4 Keypoint cleaning and interpolation

```bash
python -m beat2body clean --tool dwpose
```

Reads `2d/keypoints/<category>/<video_id>_<tool>.npz` and writes the training keypoints to `2d/keypoints/<tool>/<category>/<video_id>.npz` (one folder per tool):

- **Confidence thresholding:** keypoints below the tool's threshold (`--conf`) are set to `NaN`.
- **Outlier removal:** a single-frame spike, where a joint jumps away by more than 3× its median displacement and comes straight back, is marked as missing. Fast but consistent motion is kept.
- **Linear interpolation** over short gaps (≤ 5 frames, `--max-gap`) along the time axis for each joint independently.
- **Smoothing:** Savitzky–Golay filter, window 7, order 2 (`--sg-window`, 0 disables it).
- **Normalization:** the pelvis (mid-hip) is moved to `(0, 0)` and coordinates are divided by the median torso length (mid-shoulder to mid-hip) over the whole dataset. Parameters are saved to `2d/keypoints/<tool>/normalization.json`; each file also stores its `pelvis` track and `scale` to undo the normalization.
- Output arrays: `keypoints (T, 17, 2)` with longer gaps filled linearly, and `valid (T, 17)` marking which values were observed (use it as a loss mask).

### 4.5 Audio feature extraction

```bash
python -m beat2body audio --categories la_hiphop house
```

- Audio is extracted as mono 22.05 kHz to `2d/audio/<category>/<video_id>.wav`.
- **Log-mel spectrogram:** `n_mels=64`, `hop_length=735` (22050 / 30), so one feature frame corresponds to one motion frame → `features/audio_mel/<video_id>.npy` `(T, 64)`.
- **Onset strength envelope:** `librosa.onset.onset_strength` → `features/audio_onset/` `(T,)`.
- **Beats** → `features/beats/`, as beat times in motion frames (float), for the beat-alignment loss and evaluation. AIST songs have a published constant tempo (80–130 BPM; House 110–135, see [data formats](https://aistdancedb.ongaaccel.jp/data_formats/)), so their beats are a grid at exactly that tempo. Its phase comes from `librosa.beat.beat_track` where librosa found the right tempo, else from the onset envelope. librosa alone was wrong for 10 of 60 songs (80 BPM tracked as 164 or 106, `mHO5`, `mJB1`); this was fixed on 2026-11-18. For 4 songs (`mHO4`, `mJS3`, `mKR1`, `mLH4`, 12 videos) the audio cannot clearly separate beat from off-beat, so their phase may be half a beat off. `python -m beat2body beats` recomputes the beats from the onset features, and `python -m beat2body audit --tool <tool>` checks them against the published tempos.

### 4.6 Alignment

```bash
python -m beat2body clips --tool dwpose --window 240 --stride 60
```

- Motion and audio features are both at 30 fps, so **frame `t` in motion corresponds to feature frame `t` in audio**; alignment only trims both to the shorter length.
- **Variable-length videos** are cut with a **sliding window** (`--window`, default 240 frames = 8 s, stride 60). Each clip in `2d/clips/<tool>/<split>/` stores its keypoints, valid mask, audio-feature slices, beats and category label.
- `2d/clips/<tool>/meta.csv` lists every clip: `clip_path, audio_feat_path, category, start_frame, end_frame, split, video_id, dancer, music`; `split.json` records the options and the songs in each split.
- Only the cleaned keypoints and features are needed, not the videos.

### 4.7 Dataset split

The goal is not zero-shot generalization to new music, so train and val share songs. One song per genre is still held out completely, for a final check on music the model has never heard:

| Split | What goes in | Default (seed 0, DWPose) |
| --- | --- | --- |
| **test** | all videos of `--test-songs 1` song per genre (10 songs), never seen in train or val; **final evaluation only** | 489 clips, 36 videos |
| **val** | 15% of the remaining videos per genre (`--val-ratio`), split by video (`--by video`): same songs and dancers as train | 440 clips, 29 videos |
| **train** | the rest | 2155 clips, 145 videos |

Clips are never split individually (overlapping windows of one video would leak), and the split is stratified per category. Options:

```bash
python -m beat2body clips --tool dwpose                        # default above
python -m beat2body clips --tool dwpose --by dancer            # train / val by dancer
python -m beat2body clips --tool dwpose --test-songs 0 --by video   # plain per-video 70 / 15 / 15
```

**Hugging Face.** `keypoints/<tool>/`, `features/`, `clips/<tool>/` and `categories.json` are published as one dataset per tool, with the same paths under `2d/`:

| Dataset | Tool |
| --- | --- |
| [`SizheZ03/AISTDance_dwpose`](https://huggingface.co/datasets/SizheZ03/AISTDance_dwpose) | DWPose (recommended for training: 99.7% of joints observed) |
| [`SizheZ03/AISTDance_openpose`](https://huggingface.co/datasets/SizheZ03/AISTDance_openpose) | OpenPose (official build) |
| [`SizheZ03/AISTDance_mediapipe`](https://huggingface.co/datasets/SizheZ03/AISTDance_mediapipe) | MediaPipe |

The account comes from `--org`, `BEAT2BODY_HF_ORG` or the logged-in account (`hf auth login` / `HF_TOKEN`);
`hf upload` creates missing datasets as private (`--public` to change). `SAMBOOM/AISTDance_*` are the
original public copies with the old per-video split.

`hf download` puts a dataset in place (`data --download` does the same when `meta.csv` is missing); `hf card` writes the dataset card to `2d/hf_cards/` for review; `hf upload --prune` publishes local results with the card (source, AIST terms and citation, file format, split).

**Training data loader.** `beat2body.data.DanceClips` / `make_loader(tool, split, batch_size, seq_len=150)`
give EDGE-style windows: `motion (L,38)` = [2 ankle contacts | 2 root (pelvis in the image) | 17 x 2
pelvis-centred joints], `valid`, `root_valid`, `audio (L,37)` = EDGE's 35 baseline music features
(`python -m beat2body edge-features`, normalized with train-split statistics) + beat phase (sin, cos),
`beats` and `category`. Windows come from `meta.csv`; data is read from the per-video files. Train items
get a random crop and a left/right flip. `python -m beat2body data` checks shapes, NaNs and statistics.

**Model.** An EDGE replica (Tseng et al., CVPR 2023) adapted to 2D with a genre condition; see
`NEXT_STEPS.md` (Task 3) for the side-by-side comparison and `python -m beat2body train --help`.

**Rendering.** `python -m beat2body render --video-id <id> --overlay` writes a stick-figure video (beats flash the panel border, audio included); `--keypoints file.npy` adds a panel for a generated `(T, 17, 2)` sequence.

Pipeline outputs (frames, keypoints, audio, features, clips, cards, renders) are ignored by git.

## 6. Dance category conditioning

**Encoding:** start with a **learned embedding** rather than one-hot. The data has **10 categories** (`categories.json`, indices 0-9 in alphabetical order); a learned embedding of dimension **16** is sufficient. One-hot with a linear layer is equivalent but less flexible; a learned embedding scales to more categories by increasing `num_embeddings`.

**Where to inject:** inject the category embedding at **every decoder step**. For a GRU decoder, concatenate the embedding to the input at each time step (or add it to the hidden state via a linear projection). For a Transformer decoder, add it as a **prefix token** or as an additive bias to the decoder's hidden states. The latter (additive bias) ensures the category signal is available throughout generation, not just at the start.[^1][^2][^3]

**Inference exposure:** expose `category` as a string argument (e.g. `"la_hiphop"` or `"krump"`). Map it to an integer index via a fixed dictionary, then to the embedding. When you expand to more categories, you only need to update the mapping and retrain (or fine-tune) the embedding table; the rest of the architecture remains unchanged.

**Expansion plan:** keep the category vocabulary in a separate `categories.json` file. The model checkpoint should store `num_categories` and the embedding dimension. Adding a new category later means adding one row to the embedding table and fine-tuning on data for the new category.
